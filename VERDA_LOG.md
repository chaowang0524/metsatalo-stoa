# Verda decisions log

- 2026-11-14: `deepseek-4-1-flash-1017` silently drops images (image calls logged only 200–1100 prompt tokens), so the old cubicasa "vision fallback" was effectively guessing. Switched vision to the **Nemotron 3.5 Super VL** container endpoint (`endpoint="vision"` in `stoa/verda.py`), with `enable_thinking: false` (with thinking on, 3000 tokens went to reasoning and no answer came back).
- 2026-11-14: cubicasa5k probe on 30 drawings: **one** Nemotron call per drawing (~1.6–2.6k tokens) extracts all labels and symbols and is cached, serving all ~18 questions for that drawing (~100–150 tokens/question). Room-label questions answered by code rules: kitchens 100%, balconies 100%, floors 93–97%, WC 83%, bedrooms 67–78%. Symbol counting is weak: doors ~20%, windows ~10%, showers/sinks below the majority-class prior.
- 2026-11-14: Split endpoints into one module each under `endpoints/verda/` (deepseek, kimi, nemotron); `verda.chat(endpoint=...)` picks one. `kimi-k3-1-pro` returns 403 "project is not subscribed … at service tier standard", so it is not usable yet.
- 2026-11-14: `kimi-k3-1-pro` now works with its own key (`VERDA_KIMI`). Smoke test: 93 prompt + 1124 completion tokens, of which 907 were reasoning. Reasoning is on by default, so set `max_tokens` generously or the answer can come back empty.
- 2026-11-14: Correction: `deepseek-4-1-flash-1017` **does** see images sent as `image_url` data URIs. On a synthetic PNG it read the text "BANANA 4729" and the red square exactly. The earlier "drops images" call came from the low prompt-token counts, but the endpoint simply reports few tokens for images. DeepSeek's docs show `{"type": "file", "file_id": ...}` after a Files upload, but the Verda gateway returns 404 for `POST /v1/files` and 400 ("no file input") for inline `file` parts, so `image_url` is the only route that works. Also found that `vision_tools.ask_vision_model` never passed `endpoint`, so every "vision" call went to deepseek, never to Nemotron. Now each router model reads images itself (`endpoint=router`).
- 2026-11-14: Model benchmark, same 200 questions (40 per source, seed 0), reasoning off for all, each model reading images itself. Numeric accuracy: deepseek 70%, kimi 70%. cubicasa5k (vision): deepseek 45%, kimi **70%**. opening_design (schedule text): deepseek 24% numeric / 27% text, kimi 31% / **55%**. ifc_models: deepseek **100%**, kimi 72%, because with reasoning off kimi answered 11 Estonian room-area questions without calling a tool and made the numbers up. Cost per 1k questions: deepseek **$0.78**, kimi $15.45. Nemotron container: calls took ~270 s each (smoke test this morning was 1.8 s) even at 2 workers, so the run was stopped at 0/200. `kimi-k3-1-pro` reasoning is turned off with `extra_body={"thinking": {"type": "disabled"}}`.
- 2026-11-14: New default profile `hybrid` in `stoa/pipeline.py`: deepseek routes and composes, kimi composes answers from PDF schedule text and reads drawings with reasoning on. Reasoning on costs ~7k output tokens (~$0.075) per drawing, about 30× kimi without reasoning. The final turn now goes out without tools, so a model can't run out of turns without answering.
- 2026-11-14: Kimi vision at `reasoning_effort="low"` (with `thinking` enabled) uses a few hundred to ~1.2k reasoning tokens per drawing. The default effort used a median 4.5k and hit the 12k cap on 21 of 83 calls, and those truncated answers were scraped from the reasoning text. Hybrid with low effort on the same 200 questions: **79%** numeric (default effort 77%), 58% text (54%), cubicasa 70% (65%), $9.51 per 1k questions ($30.98), 12 s per question (30 s), 0 failures. This is now the default.
- 2026-11-14: Set Kimi's shared defaults to thinking enabled, `reasoning_effort="low"`, and `max_tokens=4096` (reasoning plus final answer). Routing, PDF text composition and vision inherit this budget; other endpoints retain their existing limits. Windows live smoke checks passed for IFC wall counting (57), PDF room-area lookup (15.61 m2), and the same lookup from a raster image (15.61 m2). All three Kimi requests used the intended settings and finished without token-limit truncation. Request settings and results are in `out/kimi_low_smoke.json`; the full benchmark has not been rerun after this change.
- 2026-11-14: `GET /models` on the Verda gateway lists only `deepseek-4-1-flash-1017` and `kimi-k3-1-pro`, so Verda has no image-generation model. The UI's 3D render (`stoa/ui/render.py`) calls Gemini `gemini-3.1-flash-image` directly and logs each call to `logs/image_calls.jsonl`.
